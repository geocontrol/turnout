# Spike: Briefcase vs PyInstaller for Turnout

**Date:** 2026-09-22
**Question:** Can Briefcase package a threaded uvicorn server with a tray icon, and if not, does PyInstaller?
**Answer:** Yes. **Briefcase confirmed as primary, PyInstaller as fallback** — but the plan's Briefcase configuration is substantially out of date and must be rewritten.

## Environment

| | |
|---|---|
| Host | macOS 26.6.2, arm64 |
| Python | 3.12.8 |
| Briefcase | **0.4.5** (plan was written against 0.3.x) |
| PyInstaller | 6.22.3 |
| Docker | 29.7.2 |

## What was actually tested

A throwaway app mirroring Turnout's real risks rather than a hello-world: uvicorn on a
background thread, pystray on the main thread, a Jinja2 template loaded from package
data, a live HTTPS request, and a QR render. It exposes `/probe`, which reports what a
packaged build could plausibly have broken.

## Results

| Check | Briefcase | PyInstaller |
|---|---|---|
| Builds at all | yes | yes |
| Jinja2 templates collected | yes | yes (needs explicit `--add-data`) |
| HTTPS / CA bundle | **yes** | **yes** |
| `qrcode` (deferred, function-level import) | yes | **yes, with no `--hidden-import`** |
| Page renders through the full stack | yes | yes |
| `sys.frozen` set | **NO** | yes |
| stdout visible when launched | **NO** (macOS `.app`) | yes |
| Produces an installer | **yes** — 46MB `.dmg`, one command | no, a bundle only |
| Architecture | universal2 (`x86_64 arm64`) | arm64 only |
| Bundle size | 180MB (universal2) | 51MB |
| Non-zero exit on failure | yes (214) | yes (1) |

## The findings that change the plan

### 1. Briefcase does not set `sys.frozen` — confirmed, and it matters

`paths.frozen()` returns False under a Briefcase build, which sends `data_dir()` to
`Path("data")` — relative to the working directory of a double-clicked app. The probe
confirmed `sys_frozen: false` and showed `cwd` as the launching shell's directory, not
the bundle.

**Verified fix:** setting `os.environ.setdefault("TURNOUT_FROZEN", "1")` in the app's
`__main__.py` flips it. `paths.frozen()` already honours that variable, so no change to
`paths.py` is needed — only the entry point. Confirmed by rebuilding and re-probing.

The docstring on `paths.frozen()` already predicted this correctly; the spike upgrades
it from a well-reasoned guess to a measured fact.

### 2. A packaged macOS `.app` produces no stdout

Running the built `Spike.app` binary directly yields nothing on stdout or stderr — the
stub routes output to the macOS unified log (hence `std-nslog` in the template's
requirements). PyInstaller, by contrast, prints normally.

**Consequence for Turnout:** `desktop.py --self-test` prints its diagnostics with
`print()`. In a packaged macOS build that output goes nowhere, which defeats the whole
point of a flag whose job is answering "it will not start — what does it say?".
Task 8 must make `--self-test` write to a file (or to the rotating log) and tell the
user where, not just print.

### 3. The plan's `pyproject.toml` is outdated in at least six ways

Generated by Briefcase 0.4.5 versus what the plan specifies:

| Plan says | 0.4.5 actually uses |
|---|---|
| `license.file = "LICENSE"` | `license = "MIT"` (SPDX id) + `license-files = ["LICENSE"]` |
| `std-nslog~=1.0.3` | `std-nslog~=2.0.0` |
| Flatpak `org.freedesktop.Platform` 23.08 | `org.gnome.Platform` 48 |
| `libgirepository1.0-dev` | `libgirepository-2.0-dev` |
| (not mentioned) | AppImage now requires `manylinux_2_28` |
| (not mentioned) | `briefcase new` rejects free-text licences; SPDX only |

Task 8 should start from a freshly generated 0.4.5 template and port Turnout into it,
not from the plan's hand-written config.

### 4. The default template is Toga-centric and must be pruned

`briefcase new` emits `toga-*` requirements and a large set of GTK build dependencies
even when the GUI framework is declined. Left in place, the Debian build fails:

```
E: Unable to locate package libgirepository-2.0-dev
```

Turnout needs none of them. Pruning `system_requires` to empty and keeping only
`gir1.2-ayatanaappindicator3-0.1` as a runtime requirement gets the Debian build moving.

### 5. Linux builds need Docker *and* an explicit `--target`

`briefcase create linux system` refuses with "can only be built on Linux, or on macOS
using Docker" even with Docker running; it needs `--target debian:bookworm` (or similar)
to select a base image.

With the Toga dependencies pruned, the Debian build then succeeds from macOS via Docker:
`Created build/spike/debian/bookworm`, with the app code and every dependency resolved
*for Linux* — `pystray`, `Xlib`, `python_xlib-0.33`, `certifi` and the rest.

That last point is worth noting against Task 7's experience. `pip-compile` silently
dropped `python-xlib` from `requirements.txt` because it resolves markers for the
compiling host only, and the lock had to be hand-patched and pinned by a test. Briefcase
resolves `requires` per target platform itself, so the packaged app does not inherit that
problem — it applies to the dev and container environments only.

### 6. `briefcase create --no-input` aborts on an existing build directory and exits 0

Verified by running it twice in succession:

```
FIRST (clean dir) EXIT=0
SECOND (dir exists) EXIT=0
Aborting creation of app 'spike'; existing application template will not be overwritten.
```

This is a real trap for Task 10. If a CI job caches the build directory, or a previous
step leaves one behind, `create` does nothing, `build` then packages whatever was already
there, and the pipeline goes green while shipping stale code. The CI workflow must either
clean the build directory first or treat "Aborting creation" in the output as a failure.

## Two false alarms, corrected

Recorded because the spike's value is partly in what it *disproved*:

- **PyInstaller and hidden imports.** The plan predicted `--hidden-import` archaeology
  for uvicorn and for Turnout's function-level `import qrcode` in the QR route.
  PyInstaller 6.22.3 found both with no flags at all. An earlier run in this spike
  appeared to show `qrcode` missing — that was my own error (it was never installed in
  the build venv), not a PyInstaller defect. Re-tested fairly, it passes.
- **Briefcase exit codes.** An apparent "exits 0 on failure" was an artefact of piping
  to `tail`. Run directly, Briefcase exits 214 on a failed build.

The `qrcode` mistake did surface one real difference: Briefcase resolves the app's
declared `requires` from PyPI independently of the build virtualenv, so it pulled
`qrcode` in regardless. PyInstaller bundles what is in the build environment, so a
dependency missing there is silently missing from the app.

## Recommendation

**Briefcase, as planned.** It produced a real `.dmg` in one command, handled a
universal2 build across two architectures including compiled wheels, and got every
runtime check right except `sys.frozen`, which has a one-line fix.

PyInstaller also worked, and worked well — better than the plan gave it credit for. It
remains a credible fallback. But it produces a bundle, not an installer, so choosing it
means adding four more toolchains to reach the same place, which is precisely the work
Briefcase removes.

**Required plan amendments before Task 8:**

1. Bump the floor from `briefcase>=0.3.17` to `briefcase>=0.4.5`.
2. Regenerate `pyproject.toml` from the 0.4.5 template; do not use the plan's version.
3. Add `TURNOUT_FROZEN=1` to `turnout/__main__.py`.
4. Change `--self-test` to write to a file, not stdout.
5. Prune the Toga/GTK system dependencies from the Linux config.
6. Note the `--target` requirement for Linux builds in the CI workflow.
